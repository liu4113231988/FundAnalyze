# 模型档案与算法记录 · 重构方案

> 版本：v1（方案评审稿） · 2026-10-22 · 作者：WorkBuddy
> 状态：待评审。评审通过后按第 6 节分期实施。

## 0. 结论：建议做，且应优先于新功能

**当前系统的结构性短板**（对照 `src/webapi.py`、`webapp/app.py` 实际代码）：

| 现状 | 代码事实 | 后果 |
|---|---|---|
| 分析结果是"一次性"的 | 结果按内容哈希存 `output/data/webcache/result_v5_*.pkl`，`JobStore` 只在内存里存任务，30 分钟 TTL 一过就整条删除 | 刷新页面 / 重启进程后，历史分析无法再打开；用户无法积累、管理自己的拟合结果 |
| "横向对比"只存在于一次分析内部 | 一次 `/api/analyze` 同时跑 N 个模型，`rank` 表 + `payload` 在同一次结果里 | 换了窗口 / 换了仓位假设 / 改了超参之后，**没有入口把两份结果放在一起比** |
| "重新学习"不留痕 | `/api/refit` 直接替换当前视图，不落任何记录 | 无法回答"上次用默认参数跑出来是多少"，超参对比无从谈起 |
| 不同样本的对比无载体 | 窗口、`equity_ratio`、`auto_equity` 是请求级参数，不持久 | "同一只基金 5 年窗口 vs 10 年窗口"这类最基本的研究问题，UI 上做不出来 |

你提的"模型主记录 + 算法子记录"正好补上这一层。**这不是加功能，是给系统补上缺失的持久化层。**

### v1 明确不做的事（控制范围）

- 不做"一个档案绑多只基金"（会让净值 / 相关性 / 结论全链路复杂化）
- 不做"候选指数池按档案裁剪"（要动 `src/config.py` 的池定义与缓存体系，风险大，列 v2）
- 不改 11 个拟合器本身（`src/models.py` 的 `MODELS` / `ModelZoo` 逻辑不动）
- 不动研究结论管线（`src/experiments.py` / `run_*.py` 那套离线研究入口）

## 1. 术语重新界定（**必须先于一切代码**）

现在"模型"一词在代码和 UI 里都专指 11 个拟合器（`MODELS`、`ModelZoo`、`model_catalog`）。引入主记录后如果不重新界定，整个 UI 会自相矛盾。建议：

| 层级 | 新术语（UI） | 旧术语 | 承载物 |
|---|---|---|---|
| 主记录 | **模型档案**（入口叫"模型库"） | 无 | SQLite `model_records` 一行 |
| 子记录 | **算法记录** | "模型" | SQLite `algo_runs` 一行 + 一个 pickle |
| 拟合器 | **算法** | "模型" | `enet_slsqp` / `lasso` / … 共 11 个 |

**代码层不改名**：`MODELS` / `ModelZoo` / `model_key` 保持原样（diff 太大、回归风险高），只在 UI 文案层做翻译。新增模块 `src/registry.py` 一律使用"档案 / 算法记录"术语。

用户侧的一句话解释：**"一个模型档案 = 一次可复现的拟合实验（绑定基金与样本设置）；档案下每选一个算法，就留下一条算法记录。"**

## 2. 需求细化（把 5 条需求变成可验收规格）

### R1 模型档案（主记录）

- 字段：名称、基金代码、分析窗口（start / end）、RBSA 配置（`window` / `refit` / `equity_ratio` / `auto_equity` / `max_rebal`）、备注、创建 / 更新时间。
- 名称默认自动生成「基金简称 @ 起~止」，可改；基金简称走 `webapi._guess_name()`。
- 一个档案绑定一只基金、一个窗口（v1）。
- 档案创建后仍可改样本配置，但**修改时明确提示**：已有算法记录不会自动重算，会被标记为「样本已变更」（见 R6），不静默失效。

### R2 算法记录（子记录）

- 业务唯一键：**(档案 ID, 算法 key, 规范化超参)**。
- 指标快照进 SQLite（列表与对比表秒开）：`oos_r2` / `oos_te` / `oos_ic` / `win` / `beta` / `vol_ratio` / `fit_r2_mean` / `elapsed` / `n_weights` / `年化alpha` / `alpha_t值`。
- 完整可视化产物（曲线、权重序列、残差、趋势）沿用 `webapi.model_payload()` 的输出，pickle 落盘到 `output/data/runs/{model_id}_{run_id}.pkl`，库里只存路径。
- 每条记录带 `data_stamp`（复用 `src.data.data_stamp()`）与引擎版本（`C.CACHE_VERSION`）。

### R3 「已存在」提示（去重规格）

添加算法时按 **(算法, 超参)** 查重，四种情况分别处理：

| 情况 | 服务端行为 | UI 行为 |
|---|---|---|
| 完全相同且数据未更新 | `409 {exists:true, reason:"duplicate", run:{…}}` | 模态：「该算法（名称，参数与已有记录相同）已存在」+ 已有记录摘要（创建时间、样本外 R²、TE）+ 三按钮：**查看已有 / 仍然重跑（替换）/ 取消** |
| 相同但 `data_stamp` 已变（行情追加） | `409 {exists:true, reason:"stale", run:{…}}` | 同上，但文案提示「底层数据已更新，旧记录基于截至 X 的数据」，引导 force |
| 同算法、**不同**超参 | 直接新建（`201`） | 列表按算法分组展示，组头轻提示「该算法已有 N 条记录」——这正是超参横向对比的依据，不能拦 |
| 上一条状态为 error | 允许直接重跑，复用同一行 | 正常进入运行流程 |

`force=true` 时**复用同一行**（保留 id 与创建时间，更新指标 / 产物 / 指纹 / 戳），不产生重复行——档案下同一 (算法, 超参) 永远只有一条记录，符合"已存在则提示"的语义。

### R4 档案内横向对比

- 范围：同一档案下勾选 ≥2 条算法记录。
- 对比内容（全部复用既有产物，不重算）：
  1. 指标对比表（每列最优高亮，黑箱模型的"权重"列标注为重要性）
  2. 拟合曲线叠加：基金 + 各记录合成基准（各自归一起点=1 后同图）
  3. 当前风格权重分组柱状图（按指数名跨记录对齐）
  4. 累计 alpha 曲线叠加（对数超额口径）
  5. 权重演化 Top8 叠加（同一指数同一颜色）
- 对比端点对曲线做降采样（沿用 `model_payload` 的 `max_points=400` 策略）。

### R5 不同档案、不同样本

- 档案级样本配置：基金代码、分析窗口、RBSA 五参。
- 档案之间完全隔离：数据面板按 (基金, 窗口) 走既有 `D.load_panel()` 缓存；算法运行使用**档案自己的** RBSA 配置（`equity_ratio` / `auto_equity` / `max_rebal` 等），不再读全局 `C.RBSA`。
- 这直接兑现"不同的模型可以选择不同的样本数据"：例如档案 A = 兴全趋势 2020~2025 满仓假设，档案 B = 同一基金 2016~2026 自适应仓位，两者的算法记录可在各自档案内对比，档案摘要页也可跨档案比「最佳 R²」。

### R6 数据更新与过期（诚实性设计，防"旧结果当最新结论"）

- 每条记录存 `data_stamp`。行情追加后 `data_stamp` 变化，列表给旧记录打「数据已更新」徽章。
- 一键「重跑」= force 重跑同 (算法, 超参)，指标与产物整体替换，创建时间保留、完成时间更新。
- 档案的样本配置被修改后，其下全部记录打「样本已变更」徽章。**不自动删除、不自动重算**——重算是分钟级操作，必须用户显式触发。

## 3. 数据模型（SQLite，stdlib `sqlite3`，零新依赖）

库文件：`output/data/registry.db`（随 `C.DATA_DIR`，天然被 `.gitignore` 覆盖）。

```sql
-- 主记录：模型档案
CREATE TABLE IF NOT EXISTS model_records (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    name         TEXT    NOT NULL,
    fund_code    TEXT    NOT NULL,
    fund_name    TEXT    NOT NULL DEFAULT '',
    start        TEXT,                       -- 分析窗口起（None = 默认滚动窗口）
    end          TEXT,                       -- 分析窗口止（None = 最新）
    rbsa_json    TEXT    NOT NULL DEFAULT '{}',   -- {window, refit, equity_ratio,
                                                  --  auto_equity, max_rebal}
    note         TEXT    NOT NULL DEFAULT '',
    created_at   REAL    NOT NULL,
    updated_at   REAL    NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_model_fund ON model_records(fund_code);

-- 子记录：算法记录
CREATE TABLE IF NOT EXISTS algo_runs (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    model_id      INTEGER NOT NULL REFERENCES model_records(id) ON DELETE CASCADE,
    algo_key      TEXT    NOT NULL,
    algo_name     TEXT    NOT NULL,          -- 冗余存名，算法表改名后历史记录仍可读
    params_json   TEXT    NOT NULL DEFAULT '{}',   -- 规范化（sort_keys）超参
    status        TEXT    NOT NULL DEFAULT 'pending',  -- pending/running/done/error
    error         TEXT,
    metrics_json  TEXT,                      -- 指标快照（R2）
    payload_path  TEXT,                      -- pickle 产物路径（R3）
    data_stamp    TEXT,                      -- 运行时的底层数据指纹
    engine_ver    INTEGER NOT NULL,          -- C.CACHE_VERSION
    stale         INTEGER NOT NULL DEFAULT 0,-- 1 = 数据或样本已变更
    elapsed       REAL,
    created_at    REAL    NOT NULL,
    finished_at   REAL
);
-- 业务唯一键的 DB 层兜底：(档案, 算法, 规范化超参) 只允许一条
CREATE UNIQUE INDEX IF NOT EXISTS uk_algo_run
    ON algo_runs(model_id, algo_key, params_json);
CREATE INDEX IF NOT EXISTS idx_run_model ON algo_runs(model_id);
```

设计要点：

1. **唯一索引兜底去重**。API 层先查后写（为了给出友好的 409 提示），DB 层唯一索引防并发双写。
2. **规范化超参**：`json.dumps(params, sort_keys=True)`，`{"a":1}` 与 `{"a":1.0}` 视为不同（显式优于隐式转换，超参对比要精确）。
3. **外键级联**：`ON DELETE CASCADE` + 应用层 unlink payload 文件（try/except，文件丢失不影响删库行）。
4. **并发**：Flask `threaded=True` 下多请求并发。`src/registry.py` 内部每操作独立连接、`PRAGMA busy_timeout=5000`，所有写操作串行化（进程内 `threading.Lock`）。单用户本地工具，这个粒度足够。
5. **启动自愈**：`app.py` 导入时把 `status='running'` 的僵死行（进程被杀留下的）统一标 `error`，提示"进程中断"。
6. **迁移成本为零**：纯新增表，不动现有 `result_v5_*` 缓存体系；快速分析继续用旧缓存，档案产物走 `runs/` 目录。

## 4. API 设计（新增，全部挂在 `/api/models` 下）

| 端点 | 方法 | 入参 | 返回 / 行为 |
|---|---|---|---|
| `/api/models` | GET | — | 档案列表：`[{id, name, fund_code, fund_name, start, end, n_algos, n_done, best_oos_r2, n_stale, created_at}]` |
| `/api/models` | POST | `{fund_code, name?, start?, end?, rbsa?{window,refit,equity_ratio,auto_equity,max_rebal}, note?}` | `201 {model}`；校验复用 `_parse_window` / 6 位代码规则 |
| `/api/models/<id>` | GET | — | 档案详情 + 全部算法记录（含指标快照，不含重产物） |
| `/api/models/<id>` | PATCH | `{name?, note?, start?, end?, rbsa?}` | 改样本配置 → 级联把子记录 `stale=1`；返回更新后的档案 |
| `/api/models/<id>` | DELETE | — | 级联删子记录行 + unlink payload 文件；`{ok:true, deleted:n}` |
| `/api/models/<id>/algos` | POST | `{algo_key, params, force?}` | 查重（R3）：`201 {run, job_id}` 或 `409 {exists:true, reason, run}` |
| `/api/models/<id>/algos/<rid>` | GET | — | 完整 payload（曲线 / 权重 / 残差 / 趋势），从 pickle 读 |
| `/api/models/<id>/algos/<rid>/rerun` | POST | `{params?}` | force 重跑，复用同行；`{run, job_id}` |
| `/api/models/<id>/algos/<rid>` | DELETE | — | 删行 + unlink 文件 |
| `/api/models/<id>/compare?runs=1,2,3` | GET | 逗号分隔 run id（2~6 个） | 横向对比包：各 run 的 metrics + 降采样曲线 + 权重 |
| `/api/models/<id>/corr` | GET | — | 该档案样本窗口的相关性分析（复用 `correlation_block`） |
| `/api/job/<jid>` | GET | — | **复用现有轮询**，`JobStore` 增加 `model_id` / `run_id` 上下文字段 |

任务执行流（worker，复用现有 `JOBS` 与并发闸门 `_JOB_SEM`）：

```
创建 run 行(status=pending) → 起线程 →
  D.load_panel(fund_code, start, end)            # 数据缓存已按窗口隔离
  ModelZoo(档案 rbsa 配置).run(panel, [algo_key], params, max_rebal)
  model_payload(rep, nav_oos)                     # 完整可视化产物
  metrics 提取 → metrics_json
  _atomic_pickle_dump(payload, runs/{mid}_{rid}.pkl)
  UPDATE algo_runs SET status=done, metrics_json, payload_path,
         data_stamp, engine_ver, elapsed, finished_at, stale=0
失败 → status=error + error 文本（payload 保留上次成功的，不误删）
```

错误码约定：`400` 参数非法（复用 `_bad`）、`404` 档案/记录不存在、`409` 已存在（带 `run` 摘要）、`429` 并发闸门满（复用现有语义）。

## 5. 前端设计

### 5.1 结构：双入口

顶栏加一组 tab，**现有单页分析原样保留**（叫「快速分析」，不落库、随开随走），新增「模型库」入口：

```
[ 快速分析 ]  [ 模型库 ]        ← 顶栏 tab
```

### 5.2 模型库三视图

**视图 A · 档案列表**（落地页）
- 卡片网格：档案名、基金简称+代码、窗口、算法数 / 完成数、最佳样本外 R²、「N 条待更新」徽章、创建时间
- 操作：打开 / 删除（删除前确认，列出将删掉的记录数）
- 「+ 新建模型」按钮 → 视图 B

**视图 B · 新建档案**
- 表单：基金代码（输入即调 `/api/name/<code>` 解析简称，失败给红字）、档案名（自动生成可改）、起止日期（默认近 5 年，复用 `windowSel` 逻辑与 2 年下限校验）
- 折叠「高级设置」：RBSA 五参（window / refit / equity_ratio / auto_equity / max_rebal），每项带 tooltip 说明（口径与现页面附录一致）
- 提交 → 创建并直接进入视图 C

**视图 C · 档案详情**
- 头部：样本配置摘要 chips（基金、窗口、Σw、自适应、重估点）+ 编辑 + 删除 + 「刷新数据」提示
- 「+ 添加算法」→ 模态：算法下拉（按 family 分组，显示 desc 与"可解释/黑箱"标签）、超参表单（**复用现有 `renderTuner` 逻辑与 `/api/catalog` 默认值**）、提交
  - 提交返回 409 时切到「已存在」模态（R3 规格），三按钮分支
- 子记录表格：算法 | 参数摘要 | 样本外R² | TE | IC | 胜率 | 耗时 | 状态徽章（运行中 / 失败 / 数据已更新 / 样本已变更）| 创建时间 | 操作（查看 / 重跑 / 删除）
  - 运行中行实时进度（轮询 `/api/job/<jid>`，复用现有 `poll()`）
- 勾选 ≥2 行 → 「横向对比」→ 视图 D
- 单行「查看」→ 单记录详情（基金 vs 合成基准曲线、残差、权重演化、当前权重、alpha 卡、趋势状态——全部复用现有图表配置）

**视图 D · 横向对比**
- 指标对比表（列最优高亮；黑箱行权重列注明"重要性排序"）
- 拟合曲线叠加图 / 累计 alpha 叠加图 / 当前权重分组柱状 / 权重演化 Top8 同色叠加
- 「导出 CSV」：指标表直接下载（研究留痕）

### 5.3 代码组织（控制 app.js 不爆炸）

- 新增 `webapp/static/library.js`（模型库 SPA 逻辑），`index.html` 以普通 script 顺序加载，不上打包器。
- **图表函数纯函数化**是前置重构：现有 `drawCurve/drawResid/drawWHist/drawWeights` 绑定全局 `state`，先重构成 `drawCurveInto(domId, payload)` 之类签名的纯函数，快速分析页与模型库页共用。此步骤单独一期 + `tests/dom_check.js` 回归，保证现有页面零行为变化。
- 深色主题沿用 `style.css` 现有 CSS 变量；新增类统一加 `lib-` 前缀避免撞名。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 术语混淆（"模型"一词两义） | 第 1 节的术语表作为评审共识；UI 文案全局过一遍；代码层不改名 |
| `app.js` 已 1800 行，继续膨胀 | `library.js` 独立文件；图表函数抽共享纯函数；新 CSS 类 `lib-` 前缀 |
| SQLite 并发写 | 进程内写锁 + `busy_timeout=5000` + 唯一索引兜底；单用户本地场景足够 |
| DB 行与 pickle 产物不一致 | 原子写（复用 `_atomic_pickle_dump`）；写产物失败 → 该行 error 但保留上次成功产物；删档案时文件丢失只 warning |
| 删档案误删 | 前端二次确认并列出记录数；级联只删本档案的 run 文件 |
| 数据追加后旧记录被当最新结论 | `stale` 徽章 + `data_stamp` 显式展示；对比表对 stale 行加角标 |
| 大 payload 传输卡 UI | compare 端点降采样；单记录详情按需加载（列表不传重产物） |
| 与现有缓存体系冲突 | 完全隔离：旧 `result_v5_*` 服务快速分析，新 `runs/` 服务档案；`CACHE_VERSION` 变更时旧档案记录标 stale 而不是失效 |

## 8. 开放问题（需你拍板）

1. **档案是否支持多基金？** 建议 v1 不支持（一只基金一个档案），多基金会让净值 / 相关性 / 结论全链路复杂化，且研究上极少需要。
2. **候选指数池是否按档案可配？** 建议 v2（要动 `src/config.py` 池定义与缓存键，本期风险大于收益）。
3. **回测入口与结果归属？** 建议：档案详情页每条算法记录带「回测」按钮（复用 `backtest_fund`，样本配置取档案）；回测结果 v1 不入库，独立展示——避免子记录语义混入"拟合结果"与"回测结果"两种东西。
4. **去重粒度**：本方案按 (算法 + 超参) 去重、同算法不同参数允许并存。若你要求"同算法只准有一条"，超参对比就没了，与 R4 冲突——建议维持本方案。
5. **快速分析页是否保留？** 建议保留作为"不落库的临时实验"，并加「保存为模型档案」按钮把当前结果一键转存（v1.1）。

## 9. 与既有功能的关系（不变式）

- `/api/analyze`、`/api/refit`、`/api/backtest`、`/api/corr`、`/api/catalog` **全部不动**，快速分析继续服务。
- `src/models.py`、`src/rbsa.py`、`src/webapi.py` 的分析引擎**不改逻辑**，registry 只做编排与持久化。
- 方法论纪律不变：档案下的算法记录同样遵守"只看样本外 R²""黑箱权重不可当持仓""黑箱 vs 线性分开表述"等既有口径（`build_insights` 的结论生成逻辑可被档案详情页复用）。
- 回测页的"恒定仓位对照"纪律不变：模型库若提供回测入口，必须同样带对照组。
